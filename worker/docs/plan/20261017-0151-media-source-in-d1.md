## Context

- Today the media module's 21 source tables (`media_*`, `modules/media/schema.ts`) are part of the Durable Object's SQLite (`src/db/schema.ts` re-exports them; DO migrations 0011 and 0012). The admin API runs inside the DO and reaches them through `c.get("db")` (93 call sites in `modules/media`). The read model (`rm_*`) already lives in the D1 database `tv-bk-io` (binding `MEDIA`, `apps/api/d1/media/0001_init.sql`), written by `projector.service.ts` and read by the stateless Worker.
- `workers/db.ts` explains why the app as a whole is on DO SQLite: many small queries per request and 20+ interactive read-then-write transactions. The media module uses `db.transaction()` in 27 places (titles 3, seasons 5, live 7, playable 3, images 2, people 2, taxonomy 2, collections 1, rows 1, import 1, plus the test adapter).
- drizzle's D1 driver implements `transaction()` as separate `begin` / `commit` statements, which D1 rejects; D1's only atomic unit is `batch()` (one implicit transaction per call, results per statement, `RETURNING` allowed). drizzle's libsql driver, which the Bun tests use, supports `batch()` too.
- Client-visible ids (titles, seasons, people) are `AUTOINCREMENT` integers: sequential, so anyone holding a subscription token can enumerate `/titles/t1`, `t2`, … and a child row cannot be written in the same batch as its new parent. The user asked for random ids (nanoid) instead. `shared/lib/id.ts` has an 8-character `nanoid` (36-letter alphabet) and a ULID; the read model (`rm_titles.id INTEGER`, `rm_seasons`, `rm_people`, `rm_cms_items.title_id`), the Worker's id parsing (`app.ts#numericId`, `cms.ts`), the console (`Title.id: number`, 35 numeric id fields in `-media-api.ts`, `intParam` on 28 routes) and the `hero_title_ids` setting all assume integers. The RN client treats CMS `vod_id` as an opaque string.
- The backup module (`modules/backup/export.service.ts`, `restore.service.ts`) walks each contribution's drizzle tables through the app database; a contribution has no database handle of its own.
- `entry.ts` installs the read-model handle at DO boot (`setReadModelDb(env.MEDIA)`); `app.ts` seeds the media taxonomy and `tvbox/publish.service.ts` projects the library from `db`.
- CI applies `d1/media` migrations with `wrangler d1 migrations apply MEDIA --remote`; the smoke test applies them `--local` before `wrangler dev`.
- D1 limits that matter: 100 bound parameters per statement (same as DO SQLite), no `BEGIN`, one primary location (every query from the DO is a network round trip of a few to tens of milliseconds), a paid plan includes 50 million row writes a month (a 5000-title import writes about 300 thousand rows).

## Proposal

The media module gets its own database handle, a drizzle D1 database over the `MEDIA` binding; the DO keeps running the media admin API (auth, token scopes, audit, console unchanged) but stores no media rows. Nothing changes for the console, the client-facing API, the import script or the workflow.

### 0. Random ids for titles, seasons and people

- `media_titles.id`, `media_seasons.id`, `media_people.id` become `TEXT PRIMARY KEY`, generated by a new `mediaId()` in `shared/lib/id.ts`: 12 characters from the 36-letter alphabet (about 4.7 × 10^18 values), so an id cannot be guessed or counted up from a neighbour. Internal rows keep their ULIDs. Foreign keys (`title_id`, `season_id`, `person_id`, `owner_id`, row items, credits, external ids, the hero setting) follow.
- Ids are used bare everywhere, no type prefix (user decision): a title is `k7m2p9qx4t1z`, not `tk7m2…`. Episodes keep their ULIDs, also bare. Where one endpoint or table mixed kinds by prefix, the kind becomes explicit instead: `rm_playback` and `rm_cms_items` are keyed by the bare title / episode / season id (unique across tables, random); `rm_search` gets a `type` column (`title` / `person`) and the search response carries it; `/playback/:id` looks the id up by primary key; home and row items reference bare title ids; the hero setting holds bare ids. The read model's id columns become `TEXT` (migration `0002` recreates the `rm_*` tables; the next publish rebuilds them), the Worker stops converting ids to numbers, the contract's doc comments drop the `t…` / `e…` wording, and the console's media types and routes take string ids (`idParam` instead of `intParam`).
- Because every id is known before its insert, a create and all its children fit in **one batch**: the two-step create of the first draft of this plan is no longer needed, and every media mutation is atomic again.
- What this does and does not protect: ids can no longer be enumerated, but `/browse`, `/search` and the CMS list still page through the whole published library for anyone with a subscription token. Bulk collection through those endpoints is a separate concern (per-token rate limits or page caps), not part of this plan.

### 1. Database seam (`modules/media/db.ts`)

- `MediaDb`: the libsql-flavoured drizzle type over the media schema, the same trick `db/types.ts` uses; `createMediaDb(d1)` wraps `drizzle(d1, { schema })`, normalising `run()` to carry `rowsAffected` where the module reads it. `setMediaDb` / `getMediaDb` like the read-model store; `mediaDb(c)` for routes throws 409 `MEDIA_DB_UNAVAILABLE` when the deployment has no binding (the rebuild route already behaves so).
- The media schema stops being part of `src/db/schema.ts`'s re-export for queries, but stays in the drizzle-kit snapshot for this release so no `DROP TABLE` is generated (see *Data carry-over*).
- Tests: `test-db.ts` opens a libsql file and applies the SQL files of `d1/media/` in order, so the suite runs the DDL D1 runs; the read-model adapter stays.

### 2. D1 migration `d1/media/0002_source_tables.sql`

The DDL of DO migrations 0011 and 0012 verbatim (tables, indexes, foreign keys). Source and read model share the database; names do not collide (`media_*` vs `rm_*`).

### 3. Transactions → batches (27 sites)

- Every mutation becomes one `db.batch([...])`: creates with their relations, updates with their relation rewrites, deletes with their owned images / external ids, reorders, live groups and channels, rows and hero, taxonomy seeding. With ids generated up front (section 0) nothing has to wait for a `returning`, so each batch is one atomic unit.
- Import: per title, (1) one batch of lookups (title by external id, people by external ids, existing seasons and images), (2) one batch of writes (title, genres, translations, external ids, images, seasons and their posters, new people, credits). Two round trips per title; the service's public behaviour and `import.test.ts` stay (ids in the tests become strings).
- `loadLibrary` becomes one batch of selects.

### 4. Boot and callers

- `entry.ts`: `setMediaDb(env.MEDIA ? createMediaDb(env.MEDIA) : null)` next to `setReadModelDb`; `app.ts`: `initMedia(getMediaDb())` (skips seeding without a binding); `tvbox/publish.service.ts`: projects from the media handle.
- Routes: `c.get("db")` → `mediaDb(c)` in the media routes; `record()` keeps the DO database for audit.

### 5. Backup

`BackupContribution` gets an optional `db: () => MediaDb | null`; export and restore use it for that contribution's tables and skip the contribution with a note when it returns null. Restore writes in batches of 400 statements.

### 6. No data carry-over

The deployment's library holds nothing worth keeping (user decision), so there is no copy: the media tables leave `src/db/schema.ts` and DO migration `0013_drop_media.sql` drops them (children before parents, since the DO enforces foreign keys and the tables may hold rows). D1 starts empty; the first publish after the deploy fills the read model again.

### 7. Tests and gates

- Media services: the existing suites on the libsql + D1-DDL database; new cases for the two-step creates (child failure leaves a parent, repeat succeeds) and the backup contribution handle.
- `bun run check`, then `bun run test:workers` (local D1 through `wrangler dev` now exercises every media route and the projection).

## Risks

- **No rollback across steps**: a failure between a parent insert and its children leaves a partial record (see 3). Rare on an admin tool; the data stays consistent at the foreign-key level because children are never written before parents.
- **Latency**: every media admin query is a network round trip. Lists stay at a handful of queries; the import grows from ~0.5 s to 2–5 s per batch of 50 (5000 titles: 5–10 minutes). Publish reads in one batch, writes as before.
- **Dialect drift**: tests run on libsql, production on D1. Both are SQLite; the DDL is shared; the smoke test covers the D1 path end to end.
- **Data loss by design**: the DO's media rows are dropped at the first boot after the deploy; nothing is copied. Until the next publish the read model is empty, so the subscription's media rows and CMS lists are empty for that window.
- **Id change is breaking for anything that stored a media id**: the library has not shipped to clients beyond the smoke test and the console, and the recommendation home does not use library ids, so nothing known breaks; the read model is rebuilt on the next publish, and a device that cached a detail page sees a 404 until it reloads the list.

## Scope

- `src/db/schema.ts`, `workers/entry.ts`, `app.ts`, `modules/tvbox/publish.service.ts`, `modules/backup/registry.ts`, `export.service.ts`, `restore.service.ts`.
- `shared/lib/id.ts` (`mediaId`), `modules/media/schema.ts` (text ids), `modules/media/contract.ts` comments, `readmodel/documents.ts`, `readmodel/cms.ts`, `workers/media/app.ts`, `workers/media/cms.ts`, `workers/media/query.ts` (string ids).
- `d1/media/0002_source_tables.sql` (source tables and the `rm_*` tables recreated with text ids), tests, `README.md` (architecture paragraph), `docs/plan/media-library.md` (deviation note: text ids, D1 source).
- `apps/web/src/app/routes/_app/admin/-media-api.ts` and the `-media-*.tsx` files that carry numeric ids (about 7 files, type and route-parameter changes only).

Not in scope: serving clients from the source tables instead of the read model, moving any other module to D1, an import endpoint outside the DO.

## Alternatives

- **Serve straight from D1 source tables and drop the read model**: one copy of the data, but every client request would assemble cards, CMS items and facets from joins, and search would need FTS over source rows. The projection exists to make those cheap; keep it.
- **Move the whole app to D1**: the policy engine and the account module need interactive transactions and many small queries per request (`workers/db.ts`); out of scope.
- **Keep the DO and only add a D1 import path**: rejected by the user.
- **A media API outside the DO with its own auth**: possible later since the Worker has the binding; today the DO path gives session auth, token scopes and audit for free.

## Annotations

- 2026-10-17 (user): titles, seasons and people get nanoid ids so the catalogue cannot be enumerated — folded in as section 0; it also removes the two-step creates.
- 2026-10-17 (user): no carry-over of the deployment's media rows; the DO tables are dropped in this release.
- 2026-10-17 (user): no type prefixes on ids; the kind is carried explicitly where it was inferred from the prefix (search `type` column, keyed read-model tables).
- 2026-10-17 (implementation): done as planned, with these deviations. `createMediaDb` does not normalise `run()` (nothing in the module reads `rowsAffected`); routes call `requireMediaDb()` rather than a `mediaDb(c)` helper. Multi-row inserts go through `insertRows()` in `modules/media/db.ts`, which sizes each statement from the first row's bound parameters, because drizzle binds defaulted columns too (a 30-row episode insert overran D1's 100-parameter limit in the smoke test). The import reads an existing title's state in one batch and writes in one batch; people are looked up in a separate read beforehand. The read model's search gets `type` via `d1/media/0002_source_tables.sql`, which also recreates the `rm_*` tables with text ids. The backup restore writes external modules in batches of 200 statements, after the Durable Object's transaction committed. Media tests run on an in-memory libsql database that applies the `d1/media/*.sql` files. The DO migration is `0013_drop_media.sql`.
